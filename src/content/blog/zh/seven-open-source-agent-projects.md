上一篇我说，不建议再把 RAG 当成简历里的主项目。

然后问题马上就来了，不写 RAG，那 Agent 项目到底能做什么？？？

说实话，这类推荐我也有点心理负担。一个仓库能跑，不等于它适合直接写进简历。把 README 换个名字、界面改个颜色，面试官多问两句，还是容易露馅。

所以这次我整理了 7 个值得看的开源仓库。不是让你把它们全抄一遍，而是想帮你看清两件事。

前 4 个看具体场景，找项目选题。后 3 个看 Agent 本身怎么设计，读模型、工具和上下文如何配合。

先看场景。

**1. [SQLBot](https://github.com/dataease/SQLBot)**

SQLBot 做的是智能问数，用户用自然语言查询数据库，系统生成 SQL，再把结果呈现成数据和图表。

它值得看的地方不只是 Text-to-SQL。真实业务里，生成一句能执行的 SQL 只是起点。业务术语怎么理解，查询结果准不准，不同用户能看到哪些数据，这些才是项目真正的工程难点。

仓库里已经包含 RAG、术语库、SQL 示例校准、工作空间隔离和细粒度数据权限。你如果想做企业数据 Agent，可以重点研究它怎样把模型能力放进一套可控的数据边界里。

**2. [OpenBiliClaw](https://github.com/whiteguo233/OpenBiliClaw)**

你在 B 站喜欢的内容，小红书和抖音未必知道。

OpenBiliClaw 想解决的就是这个问题。它把分散在多个平台的兴趣信号连起来，主动寻找内容，解释为什么推荐，再根据喜欢、不感兴趣、收藏和对话继续调整结果。

我觉得这个项目最有意思的不是推荐算法，而是反馈闭环。收集偏好、建立画像、跨平台找内容、解释推荐理由、接收反馈，然后影响下一轮结果。

如果你想做个性化 Agent，这条链路比单独做一个聊天框完整得多。它还强调本地运行，画像和行为数据保存在本机，这块也很适合继续研究隐私边界。

**3. [DeepTutor](https://github.com/HKUDS/DeepTutor)**

普通 AI 问答经常是一问一答，回答结束，学习也跟着结束了。

DeepTutor 更关注持续学习。问答、测验、研究、可视化、解题和学习路径，共用一套能力运行时与学习上下文。知识库、笔记、题库和记忆，也能在不同学习流程里继续使用。

想做教育类 Agent 的朋友，可以重点看它怎样把「检索到答案」延伸成「陪用户学会一个主题」。这里面不只有 RAG，还有学习状态、任务安排、掌握度和可恢复进度。

教育 Agent 真正难的，从来不是答出一道题。

而是知道用户学到哪了，下一步该学什么。

**4. [AI-Meeting](https://github.com/lishuangqiang/AI-Meeting)**

AI-Meeting 是一个 Java 模拟面试项目。用户上传简历后，系统会围绕简历生成问题，组织答题、追问、评分，并在结束后保留逐题回放和综合建议。

它值得看的地方，是把多个 AI 步骤接进了一个真实业务流程。出题官、提问官、评分官和追问官不是孤立的 Demo，它们要共享会话状态，还要处理断线恢复、重复调用和结果回放。

做 Java 后端的朋友，可以顺着这个项目研究 Spring AI、SSE、WebSocket、MongoDB 和 Redis 怎么一起服务长会话。相比再做一个套壳聊天页面，这种完整流程更容易讲清楚业务价值。

前 4 个看完，你应该能发现一个共同点。

好项目不是先决定用哪个框架，再硬找一个场景。它们都是先有一条真实业务链路，再决定模型应该在哪一步出现。

接下来这 3 个，重点就不再是选题了，而是 Agent 自己怎么跑。

**5. [OpenManus](https://github.com/FoundationAgents/OpenManus)**

OpenManus 更适合拿来理解通用 Agent。

你可以从一个任务出发，跟着代码看模型如何选择能力、调用浏览器，再把工具结果带回后续步骤。仓库默认接入 Browser Use，也提供数据分析与可视化 Agent。

如果你还分不清「模型回答问题」和「Agent 调用工具完成任务」有什么区别，可以从这里开始读。重点别只盯最终回答，去看每轮工具调用前后，状态是怎么变化的。

**6. [Pi](https://github.com/earendil-works/pi)**

Pi 是一个精简、可扩展的 Agent harness，也就是把模型接入、工具循环和交互界面组织起来的一套运行骨架。

它提供统一的多模型 API、Agent 核心和编程 Agent 命令行工具，也能通过 Extensions、Skills 和 Prompt Templates 定制工作流。Pi 默认没有把子 Agent、计划模式之类的功能全塞进去，而是把选择留给使用者。

这点其实很值得看。

很多人做 Agent，第一反应是把规划、反思、记忆、多 Agent 全装上，恨不得一张架构图塞满整个屏幕。Pi 反过来问了一个更重要的问题，你的 Agent 到底需要哪些能力？

**7. [Deep Agents](https://github.com/langchain-ai/deepagents)**

Deep Agents 是 LangChain 的开源 Agent harness，面向长时间、多步骤任务，已经组合了子 Agent、文件系统、上下文管理、持久记忆、人工审批、Skills 和工具接入。

一个任务需要先搜集资料，再写入文件，并检查结果时，你可以研究它如何拆分任务、隔离子 Agent 上下文，以及怎样把过长的工具输出转存到文件。

它适合已经做过简单工具调用，下一步想处理长任务和多 Agent 协作的开发者。别一上来就抄完整框架，先选一条执行链，看看每一步为什么存在，失败之后又从哪里恢复。

7 个仓库看完，还是回到最开始的问题。

想找项目选题，先看前 4 个。想研究 Agent 怎么实现，再看后 3 个。

也别给自己定一个「把 7 个仓库全部读完」的宏大目标。先选一个最接近你技术栈的项目，跑起来，画出它的一条主流程，再顺着一次真实请求读代码。

能把一条链路讲明白，比收藏 100 个仓库有用。

你最想让我先拆哪一个？
